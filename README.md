# HA Migration

A data migration utility designed to ingest data from CSV files and transform each row into itemized OpenMRS entities 
formatted for OpenMRS DB Sync. Messages are published to an Apache ActiveMQ Artemis queue for consumption by the OpenMRS 
DB Sync Receiver. See [OpenMRS DB sync](https://github.com/mekomsolutions/openmrs-dbsync) project.

## Architecture Overview

The migration pipeline operates through a modular ingestion and itemization lifecycle:

1. **CSV Ingestion & Deserialization**:
   The `Processor` uses `CsvParser` (powered by Jackson CSV) to stream rows from a specified CSV file and map each row 
   into a **Root Data Model** object (e.g., `PatientData`, `EncounterData`).
2. **Itemization (`BaseRowItemizer`)**:
   A root record represents the top-level entity in the CSV file and encapsulates data spanning multiple related OpenMRS 
   database entities (for example, an Encounter containing multiple Observations). A dedicated Spring component 
   extending `BaseRowItemizer<T>` decomposes each root object into a list of `BaseEntity` instances, establishing 
   deterministic UUIDs and relational links.
3. **OpenMRS DB Sync Transformation & Transmission**:
   Each itemized `BaseEntity` is wrapped inside a `SyncModel` which matches that from the OpenMRS DB sync, each entity 
   maps it to its corresponding OpenMRS DB Sync model class name (e.g., `org.openmrs.eip.dbsync.model.PatientModel`, 
   `org.openmrs.eip.dbsync.model.EncounterModel`, `org.openmrs.eip.dbsync.model.ObservationModel`).
4. **Queue Publishing & Resume Tracking**:
   Batches of JSON messages are published to ArtemisMQ. The migration offset is saved in a `<entity_type>-offset.json` 
   file after each batch to support seamless resume capabilities.

## How To Build
Run the command below,
```
mvn clean install
```

## How To Run Application
- Prepare the values for required [environment variables](#configuration)
- Run the application with the command below

```shell
java -jar ha-migration-{VERSION}.jar --type=patient --file=patients.csv
```
The type argument specifies the EntityTpe name, and the file argument specifies the filename of the CSV file to be 
ingested.

> [!IMPORTANT]
> When the application starts ingesting a file, it can't be edited until the entire file is processed.

## Developer Guide

To extend the application to ingest and itemize a file containing a new Root entity type (for example, Encounters 
containing multiple Observations), follow the step-by-step guide below.

```
+--------------------+       +-----------------------+       +-------------------------+       +------------------------+
|      CSV File      | ----> |    Root Data Model    | ----> |      BaseRowItemizer    | ----> |   OpenMRS DB Sync      |
|  (e.g., encounters)|       | (e.g., EncounterData) |       | (e.g. EncounterItemizer)|       |   JSON -> ArtemisMQ    |
+--------------------+       +-----------------------+       +-------------------------+       +------------------------+
```

---

### Step 1: Create the Root CSV Data Model

Create a POJO representing a single root record (row) in the CSV file.

In this example, each CSV row represents an OpenMRS Encounter containing clinical observations:

```java
public class EncounterData {

    private String patientId;

    private String encounterDatetime;

    private Double systolic;

    private Double diastolic;

    private Double temperature;
}
```

### Step 2: Define OpenMRS Entity Models (`model` package)

Ensure all OpenMRS target entities generated by itemization are defined by extending `BaseEntity`.

In OpenMRS, an Encounter links to a Patient; and an Observation (Obs) links to a Patient (Person), an Encounter, and a 
Concept.

#### Encounter Entity
```java
public class Encounter extends BaseEntity {

    private String encounterTypeUuid;

    private String patientUuid;

    private LocalDateTime encounterDatetime;

    @Override
    public String getUuidTextPrefix() {
        //MUST return a unique and reproducible value
        return "...";
    }
}
```

#### Observation (Obs) Entity
```java
public class Obs extends BaseEntity {

    private String personUuid;

    private String encounterUuid;

    private String conceptUuid;

    private LocalDateTime obsDatetime;

    private Double valueNumeric;

    private String valueText;

    private String valueCodedUuid;
}
```

**Key BaseEntity conventions:**
- `uuid`: Primary UUID of the OpenMRS record.
- `creatorUuid`: Light reference string formatted as `org.openmrs.eip.dbsync.entity.light.UserLight(<UUID>)`.
- `dateCreated`: Creation timestamp (`LocalDateTime`).
- Related entity references must use light reference notation, e.g.:
  `org.openmrs.eip.dbsync.entity.light.PatientLight(<PATIENT_UUID>)`,
  `org.openmrs.eip.dbsync.entity.light.EncounterLight(<ENCOUNTER_UUID>)`.

---

### Step 3: Register DB Sync Class Mappings

1. Add the sync model and light entity class names in `Constants`:

```java
public final static String SYNC_CLASS_ENCOUNTER = SYNC_PKG + "model.EncounterModel";
public final static String SYNC_CLASS_OBS = SYNC_PKG + "model.ObservationModel";

public final static String SYNC_CLASS_ENCOUNTER_LIGHT = SYNC_PKG + "entity.light.EncounterLight";
public final static String SYNC_CLASS_ENCOUNTER_TYPE_LIGHT = SYNC_PKG + "entity.light.EncounterTypeLight";
public final static String SYNC_CLASS_CONCEPT_LIGHT = SYNC_PKG + "entity.light.ConceptLight";
```

2. Register the mapping between your `BaseEntity` classes and their sync model class names in `MessageUtils`:

```java
private static final Map<Class<? extends BaseEntity>, String> TYPE_TO_SYNC_CLASS_MAP = Map.of(
    Patient.class, Constants.SYNC_CLASS_PATIENT,
    PatientIdentifier.class, Constants.SYNC_CLASS_ID,
    PersonAddress.class, Constants.SYNC_CLASS_ADDRESS,
    PersonAttribute.class, Constants.SYNC_CLASS_ATTRIBUTE,
    PersonName.class, Constants.SYNC_CLASS_NAME,
    Encounter.class, Constants.SYNC_CLASS_ENCOUNTER,
    Obs.class, Constants.SYNC_CLASS_OBS
);
```

- Implement `itemize` method to decompose the root object into individual OpenMRS entities e.g. EncounterData -> 
  Encounter and Observations.

```java

        List<BaseEntity> entities = new ArrayList<>();

        // 2. Create and add Child Observations to the list (Systolic, Diastolic, Temperature)

        return entities;
    }
}
```

### Step 5: Register the Enum in `EntityType`

Add the new Root entity type to `EntityType` enum with its target class and estimated/maximum item count per row (used 
to pre-size batch collections):

```java
public enum EntityType {

    ENCOUNTER(EncounterData.class, 10);
    
}
```

---

### Step 6: Add Configuration Properties (Optional)

If your new entity requires specific UUIDs (such as Encounter Type UUIDs, Concept UUIDs, or Location UUIDs), declare 
them in `application.properties` and add corresponding property constants in `Constants.java`:

```properties
encounter.type.uuid=${ENCOUNTER_TYPE_UUID}
concept.uuid.systolic=${CONCEPT_UUID_SYSTOLIC}
concept.uuid.diastolic=${CONCEPT_UUID_DIASTOLIC}
concept.uuid.temperature=${CONCEPT_UUID_TEMPERATURE}
```
